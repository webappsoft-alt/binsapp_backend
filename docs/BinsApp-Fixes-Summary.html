1. Authentication & OTP

FIX "OTP limit exceeded" on all numbers (static & real)

Problem: Every number, including static test numbers, hit rate limits; +92 numbers were blocked by region gating; the express limiter bucketed everyone under a single unknown key.
Fix:
  • Static test numbers now fully bypass Redis + express limiters and use fixed OTP 1234.
  • Allowed +92 region; raised per-day cap; limiter now falls back to a per-IP bucket when phone is missing.
  • Twilio Verify path confirmed; static numbers skip Twilio send entirely.
Files: utils/staticOtpPhones.js, utils/otpProtection.js, config/env.js, modules/auth/routes.js

ADD New static test numbers

Added +923467893622 and +923703839371 as static test numbers (login with OTP 1234, no rate limits).
Files: utils/staticOtpPhones.js

CONFIRM send-otp hash & SMS Retriever behavior

  • Endpoint accepts optional 11-char app hash; it is preserved through validation and forwarded to Twilio as AppHash (uses the client's per-install hash, no hardcoded fallback).
  • Twilio Verify composes the SMS body and appends the hash on the last line automatically.
  • Added a server log confirming the hash was forwarded (appHashForwarded, appHashLength).
Action item (Twilio console, not code): set Verify Service Code Length = 4 if the app expects 4-digit SMS codes — real codes are otherwise 6 digits.
Files: utils/sendOTP.js, modules/auth/controller.js

2. Dispatch (Uber-style Priority)

ADD Multi-wave priority dispatch with immediate-dispatch fallback

Problem: With tiers configured but no operators holding real tier data, every booking still scheduled a delayed first wave (~40s) — customers waited for nothing in the early launch phase.
Fix: If no meaningful tier/score data exists among matched operators, skip all delays and notify everyone immediately. Waves resume automatically once real tier data accrues.
Files: utils/dispatchService.js, utils/dispatchWorker.js

FIX Notify all eligible owners + "missed opportunity" message

  • Confirmed all eligible owners are notified when a customer books.
  • When one owner accepts, the others get a request-unavailable event + a "you missed this one, stay tuned" notification.
Files: socket/socket.js, utils/orderMessages.js

3. Dumpster Matching Consistency

FIX /api/dumbster/nearby vs availability check disagreed

Problem: nearby showed sizes that could not actually be booked (ignored radius, real capacity, and booking conflicts).
Fix: Centralized matching logic using capacity-aware calculation (quantity − overlapping bookings). Removed date filter from nearby (dates are chosen on a later screen).

4. Payments & Ledger

MONEY Add-on fees split correctly (driveway / insurance)

Problem: The 15% admin commission was applied to the entire order total, including the flat add-on fees.
Fix: Insurance ($39) and driveway ($50) protection now go 100% to admin; the 15% commission applies only to the remaining base amount. Backfilled pending orders (incl. QQadu).
Files: utils/paymentHold.js, scripts/backfill-order-amount.js

FLOW Capture on owner-accept (was capturing at completion)

Card is now captured when the owner accepts (matching business intent and avoiding the 7-day Stripe hold expiry). Funds sit on the platform account and transfer to the owner on completion. Rollback restores inventory/status if capture fails.
Files: socket/socket.js, utils/StripePayment.js

FIX Refunds work for uncaptured holds

Admin cancel now cancels uncaptured PaymentIntents and refunds captured ones, normalizing success detection.
Files: utils/StripePayment.js, modules/order/service.js

10. Partner Services — Tree & Junk Removal

DIAGNOSE "Rejected on admin, pending on app"

Finding: The application's real status in the DB was pending; the backend returns the same status to both app and admin. The admin panel was deriving "rejected" from the per-document approval checkboxes (all false on a new application). This is an admin-frontend display issue, not a backend bug.
Recommendation: Admin UI should render the status field directly; only treat as rejected when status === "rejected".

ServiceRequiredOptional

Admin/review fields (status, notes, all is*Approved + *_note, userId, bookings) must not be sent by the apply form. On every resubmit the backend forces status: "pending". Note the field-name quirk: junk uses isCOIAApproved, tree uses isCOIApproved.
